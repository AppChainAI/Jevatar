# Jevatar 未来方向探索

## 项目定位与现状

Jevatar 更适合成为**不会说话、但有反应的伙伴**，而不是给聊天机器人换一张脸。它的特点是：用户输入文字，Jev 从固定选项中判断反应，Blobatar 用表情和动作呈现；不生成文字回复，也不展示聊天记录。

目前已有 16 种反应（包括默认、思考、肯定和否定），最近几轮交互仅保留在浏览器内存中。它能看向指针，但主要仍是被动回应：用户发来一句话，它表演约两秒，然后回到平静。还没有持续的关系状态，也不会主动开启互动。

关键问题不是“还能加多少表情”，而是：**表情能否成为用户与它双向交流的语言？**

## 值得探索的方向

### 1. 游戏：让表情成为玩法

- **猜反应**：用户先预测它的表情，再输入一句话，看它如何回应。可以借此发现人和模型对同一句话的理解差异。
- **短回合选择游戏**：用表情、点头摇头、少量图形选项推进互动，不依赖角色对白。
- **模仿与逗弄**：用户尝试让它露出指定表情；它的反应构成即时反馈。

这是最适合先验证的方向：现有能力足以构成一个游戏回合，试错成本低。游戏若需要客观输赢，规则应由代码判定，而不是让表情分类结果充当事实裁判。

### 2. 陪伴：从单次回复到关系延续

- 记住少量用户明确表达的偏好，或保留可见、可重置的相处状态。
- 对久别重逢、反复逗弄、安抚等事件产生有连续性的反应。
- 允许用户用点击、选择或停留等简单动作回应它，而不总要输入文字。

陪伴感来自可理解的连续性，而非无限堆叠“人格设定”。先验证用户是否能察觉并喜欢这种变化，再决定是否需要长期记忆。不能把模型推断的情绪当成用户的事实，更不应让它声称理解或诊断用户。

### 3. 具身智能：先有感知与行动循环，再谈硬件

- **屏幕内**：视线跟随之外，尝试靠近、躲开、被触碰后回应等行为。
- **环境感知**：在用户主动授权下，试验语气、声音或姿态带来的反应变化。
- **实体化**：只有屏幕内交互已证明有价值时，再考虑桌面装置或机器人载体。

“具身”不等于加摄像头或做外壳；核心是感知环境、采取动作、再根据结果调整。音视频输入应有清晰的开启提示、关闭方式和隐私边界。

### 4. 其他：成为应用里的无语言角色

Jevatar 也可以不局限于独立聊天页面：作为游戏 NPC、桌面伙伴或应用状态的拟人化界面，对玩家行为、任务结果、环境事件给出一致的非语言反应。固定表情与动作的限制，反而有助于角色保持辨识度。

## 推荐的第一个实验

做一个**无需说明也能玩的双向短回合**：例如用户预测它的反应、输入一句话、看它表演，然后用一个简单动作回应它。先不引入持久记忆、摄像头或硬件。

观察三个问题：

1. 用户能否读懂它的表情，特别是肯定、否定、困惑等容易混淆的反应？
2. 用户是否愿意主动发起下一回合，而非只试一次？
3. 误判发生时，用户觉得好玩、可以纠正，还是觉得它不可理解？

若互动本身不成立，增加记忆或外设只会放大问题。若成立，再探索关系延续。

## 技术边界与推进顺序

Jev 适合判断语义，例如一句话是在安慰、挑衅还是邀请；游戏规则、关系状态、动作时序与权限应由代码掌管。当前的 16 选 1 混合了情绪（如开心、难过）、立场（肯定、否定）和过程状态（思考）。未来若出现组合需求，可以分开判断并由代码组合；现在不必预先建一套完整的情绪系统。

建议按以下顺序验证：

1. **可玩的短回合**：证明表情能传达意思，也能促使用户回应。
2. **轻量关系延续**：证明连续性确实增加陪伴感。
3. **环境感知**：证明新增输入带来更好的互动，而不只是更多权限。
4. **实体化或嵌入其他产品**：在交互价值明确后选择载体。

每一步优先看用户是否读得懂、是否愿意回来，而不是功能数量。
